# UniLM-Nav 도입 전 현재 주행 모델 감사

검사일: 2026-09-29. 대상: 로컬 JM 공장 H1 4대의 랙 접근과 H1_1 파지 연결.

후속 진행: 사용자 승인 후 [별도 H1 검증 모듈](../jm_lastmile_nav/README.md)을 구현했다.
정적 후보 계산·20개 회귀 테스트·재현성 검사를 완료했지만 실제 주행에는 아직 연결하지 않았다.
아래 원본 공개 코드 조사 결과와 실제 제어기/모델 보존 방침은 그대로다.

## 결론 및 실제 진행 범위

기존 보행을 버리거나 다시 학습하는 작업부터 시작하지 않는다. 현재 시스템 위에
`파지 가능한 도착 자세 선택 → 실제 이동 → 도착 상태 재검증` 계층을 붙이는 방향이 적합하다.
다만 공식 실행 코드가 확인되지 않아 **UniLM-Nav 원본 실행 코드 도입은 아직 불가능**하다.
이 문서는 감사 결과와 적용 제안이며, 자체 구현을 원본 도입으로 표시하지 않는다.

이번에 수행한 일:

- 공식 논문, 프로젝트 페이지, GitHub 저장소 검색, 저자 공개 저장소 목록 확인.
- 유일하게 확인된 공식 소개 사이트 Git 저장소를 별도 폴더에 clone하고 커밋 고정.
- 실제 로컬 보행 모델과 상위 주행 모델 2개를 CPU에 로드하여 입출력/유한값 검사.
- 현재 evaluator, 목표 좌표, IK 시작 조건, 이전 실제 평가 결과 대조.

수행하지 않은 일: 보상/목표/관절 제한 변경, 새 학습, 로봇 제어 명령,
시뮬레이션 재실행, 외부 MLLM 호출, 새 코드의 GitHub 배포.

## 논문과 첨부 개념도의 구분

논문의 핵심은 최근 관측에서 시점 선택, 작업 지점 추정, 몸체 도착 위치 추론의 세 단계다.
실제 로봇은 H1이 아니라 B2와 Z1 조합이며, 마지막 이동은 Nav2를 이용한다.
최종 방향은 추정 작업점을 바라보도록 기하적으로 계산한다.
근거: [공식 방법 소개](https://unilm-nav.github.io/),
[논문 부록 B.2/B.6](https://arxiv.org/html/2607.06537v2).

첨부 슬라이드의 `팔 도달성 → 후보 → 비용/안전 선택` 개념을 H1에 적용하는 것은
우리 시스템의 설계 제안이다. **원본 코드가 IK 후보 최적화를 구현한다고 확인한 것은 아니다.**
논문의 성공률을 H1 성능으로 전용하거나, 도착 자세 개선이 실제 파지 물리를 해결한다고 주장하지 않는다.

하위 19개에는 다리만 아니라 몸통·어깨·팔꿈치가 포함된다. 따라서 보행 중 팔 제어를

현재 파지 경로는 정지 후 상체 소유권을 IK로 넘기고, 필요한 경우 walker-arm-shield를 쓴다.

SHA-256:

- 보행: `e1caf0201a43a82ef8d9bb8d597bffa631c14ab6a3312938afd6eeb41e2b3e0a`
- model_200: `56fb8ddaec05da9342d0acaf0160048cd8361efc7b5b6525677c096dd06f49a9`

상위 학습은 기록상 1,000 iterations, 약 67.1분에 완료됐다.
하지만 실제 링 월드에서 사용·검증한 모델은 **model_200**이다.
model_999가 더 좋다는 증거는 없으며 이번에 교체하지 않았다.

지정 도킹 조건을 통과했다. 지정 초기조건 1회 결과이지 임의 위치 성공률은 아니다.
링 접촉 파지는 016/017에서 통과했지만, 028의 리프트는 `TRANSPORT_SLIP`으로 실패했다.
UniLM-Nav가 이 미끄럼/기울기 문제를 자동 해결하는 것은 아니다.

검사 증거: `artifacts/navigation_audit_20260929/navigation_contract_audit.json`.
검사 도구: `jm_coop4_rl/audit_navigation_contract.py`.
모델 검사 전후 해시가 동일하고, 새 로봇 명령은 전송하지 않았다.

## 현재 연결에서 먼저 해결할 문제

1. **물체가 아니라 고정 랙 도킹 좌표가 목표다.**
   `rack_goals.json`의 `dock_world_xy`를 향하며, H1_1의 목표는 약 (36.175, 18.255)m다.
   파지점·팔 작업공간을 고려해 계산한 목표가 아니다.
2. **방향이 고정이다.**
   `eval_fleet.py::measure()`는 `pi/2 - yaw`로 heading을 계산한다.
   새 위치에 가더라도 작업점을 향하도록 자동 갱신되지 않는다.
3. **도착 통과와 작업 가능 통과가 분리되어 있지 않다.**
   거리 0.18m, 방향 15°, 속도 0.10m/s, yaw-rate 0.15rad/s,
   기울기 15°, 1초 정지 조건 후 `grasp.start()`를 부른다.
   실제 팔 목표에 대한 사전 도달성·간섭 검증은 이 도착 gate에 없다.
4. **안전구역이 목표 좌표에 종속된다.**
   랙 배제영역 검사에서 `position - dock_world_xy`를 쓴다.
   도착 목표만 수정하면 고정 설비의 배제영역까지 이동한다.
   새 목표 기능을 연결하기 전에 실제 고정 랙 형상 기준으로 분리해야 한다.
5. **현재 상위 정책은 일반 경로계획기가 아니다.**
   관측에 물체 영상, 깊이, 점유지도, 장애물 형상이 없고 후진 명령은 0으로 제한한다.
   임의 몸체 목표만 전달해도 공장 전역 장애물을 회피한다고 볼 수 없다.
6. **Git main은 월드 스냅샷이다.**
   앞선 업로드 범위에는 주행 학습 코드·checkpoint 전체가 포함되지 않았다.
   현재 감사는 로컬 실험 파일 기준이며 main만 clone해서 이 주행이 즉시 실행되지는 않는다.

## 적용 제안 — 단계 1 별도 모듈 구현, 단계 2 이후 미완료

```text
작업 대상과 파지점
    ↓
도착 몸체 자세 후보 (x, y, yaw)
    ↓
H1 팔 도달성 + 고정 장애물/접근 경로 검사
    ↓
검증 후보만 상위 주행에 전달
    ↓
기존 고정 H1 보행 → 실제 도착·정지
    ↓
측정 몸체/물체 자세로 IK·충돌 재검증
    ├─ 통과 → PREGRASP → INSERT → GRASP
    └─ 실패 → 정지 유지 / 실패 이유 기록
```

위 구조는 우리 H1용 제안이며 UniLM-Nav 원본 구현이 아니다.
후보가 없으면 목표/관절 제한/허용오차를 자동으로 바꾸지 않는다.

### 단계 1: 별도 검증 모듈

- 기존 model_200, WB5 보행, 파지 기준점과 성공 판정은 보존한다.
- 사전 선언된 몸체 후보만 평가하고, 동일한 측정 q_safe에서 각각 시작한다.
- 위치·closing-axis와 실제 그리퍼 TCP를 사용한다. 임의 관절 각도 조정은 하지 않는다.
- IK 수렴, 실제 잔차, 관절 한계, 간섭과 접근 경로를 각각 판정한다.
- IK만 통과한 후보를 물리 안전/파지 성공으로 표시하지 않는다.
- 우선 관측된 USD 물체 자세를 사용하는 진단 버전으로 검증한다.
  이 버전은 영상 인식/MLLM이 아니며 그대로 명시한다.

### 단계 2: 기존 주행 연결

- 고정 랙 형상과 가변 도착 좌표를 분리하고, 목표 yaw를 명시적으로 전달한다.
- 학습 분포 안의 짧은 직선 접근부터 1대 H1으로 테스트한다.
- 바닥/낙상/충돌/정지 조건은 유지한다. 물리 state pose 직접 쓰기는 reset 때만 허용한다.
- 도착 후 측정 자세로 검증을 다시 수행한 뒤에만 IK로 넘긴다.
- 정면·측면 각 1280×720 영상과 phase별 수치를 저장한다.

### 단계 3: 원본 코드 또는 별도 인식 계층

- 공식 실행 코드가 확보되면 source commit·license·의존성·외부 API 요구사항을 먼저 감사한다.
- RGB-D, camera intrinsics/extrinsics, 관측 당시 robot pose가 맞물리는 입력 구조가 필요하다.
- 클라우드 MLLM을 사용한다면 비용 및 공장 영상 전송 범위를 정한 뒤 연결한다.
- 외부 모델 출력은 후보 제안일 뿐, 물리/관절 검증을 우회하지 않는다.

## 결정과 외부 검토 상태

사용자가 별도 H1 검증 모듈 진행을 승인하여 단계 1을 구현했다.
동일 알고리즘 재현이나 공식 코드 통합으로 부르지 않는다. 단계 1의 간섭 검사는
간략 형상/끝점 검사만이며, 전체 손 형상·연속 경로·자기충돌까지 완료했다는 뜻이 아니다.

Fable 상호검토는 수행하지 않았다. 최초 PATH 조회에서는 발견되지 않았으나 후속 조사에서
`C:/Users/USER/AppData/Roaming/npm/claude.cmd`를 찾았다. 내부 설계 요약을 외부 서비스로
보내는 검토 호출은 보안 검토에서 차단돼 전송하지 않았다. 이 문서와 신규 모듈은
Fable 합의가 아니라 로컬 검토 상태다. 실제 시나리오 변경이나 신규 학습은 시작하지 않았다.
